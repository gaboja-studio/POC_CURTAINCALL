# 팀 작업 안내서 — AI와 함께 기능 만들기

> 개발을 몰라도 괜찮습니다. **AI에게 정해진 말 몇 가지**만 하면 내 작업을 끝낼 수 있고,
> 다른 사람 작업과 합칠 때 생기는 문제는 AI와 PM이 막아 줍니다.

## 1. 흐름 (예: 기능 묶음 "커튼콜 연출")

```
[PM] ① 통합 공간 만들기   integration/curtain-call
[PM] ② 작업 준비         Task 폴더 + 내 전용 테스트 씬·스크립트 폴더 + 작업 브랜치
[PM] ③ 인계             "A님, Task-20260929-001 맡아 주세요"
[나] ④ 작업             AI와 대화하며 만들기 → 수시로 "저장해줘"
[나] ⑤ 제출             "제출해줘" → 합쳐 달라는 요청(PR)이 올라감
[PM] ⑥ 합치기·함께 테스트  정해진 시간에 차례로 합치고 모두 같이 확인
[PM] ⑦ 마무리           dev(팀 공용 원본)에 반영하고 정리
```

**작업자가 할 일은 ④, ⑤뿐입니다.** 합치기와 충돌 해결은 PM이 합니다.

## 2. 꼭 알아야 할 말

| 말 | 쉬운 뜻 (비유) |
|---|---|
| 브랜치 | 원본을 건드리지 않는 내 복사본 (공동 원고의 내 사본) |
| 저장(커밋) | 지금까지 한 일을 기록 (사본에 "여기까지" 도장) |
| 제출(PR) | 내 작업을 합쳐 달라는 요청 (편집자에게 검토 요청) |
| 충돌 | 두 사람이 같은 곳을 다르게 고쳐 자동으로 못 합침 |

## 3. AI에게 하는 말

| 이렇게 말하면 | AI가 하는 일 |
|---|---|
| **"Task-20260929-001 시작해줘"** | 내 브랜치로 이동 → 최신 내용 받기 → 할 일 정리 |
| **"커튼이 3초 동안 천천히 열리게 해줘"** | 만들기. 원하는 결과를 평소 말투로 설명 |
| **"저장해줘"** | 내 구역만 고쳤는지 검사 → 저장 → 올리기 |
| **"검사해줘"** | 오류·자동 테스트 결과를 쉬운 말로 보고 |
| **"제출해줘"** | 검사 → 최신 내용 합쳐 보기 → PR 미리보기 확인 → 등록 |
| **"버그 제보해줘" / "QA 요청해줘"** | 쉬운 질문 몇 개 → 미리보기 확인 → 이슈 등록 |
| **"오늘 여기까지"** | 인계 메모 정리·저장. 다음엔 새 대화에서 "이어서 해줘" |
| **"막혔어" / "이상해"** | 원인 조사. 내가 못 푸는 문제면 PM에게 넘길 내용 정리 |

- **한 가지씩, 구체적으로** 요청하세요. "자연스럽게"보다 "3초 동안, 처음엔 느리게"가 좋습니다.
- AI가 헷갈려 하면 "오늘 여기까지" → 새 대화 → "이어서 해줘".
- AI가 "PM 요청이 필요해요"라고 하면 멈추고 PM에게 알려 주세요.

## 4. 유니티 작업 규칙

**내 구역에서만 작업합니다.** PM이 Task 폴더의 `setup.md`에 적어 줍니다.

```
내 테스트 씬:     Assets/Scenes/Tests/CurtainOpen/CurtainOpenTest.unity
내 스크립트 폴더: Assets/Scripts/Curtain/      ← 기능마다 폴더가 따로 있음
수정 금지:        Assets/Scenes/ (내 Tests 폴더 제외), ProjectSettings/, Packages/
```

- 기능은 내 테스트 씬에서 만들고 확인합니다. 공용 씬은 열어 보기만 합니다.
- **지금 작업 중인 다른 사람의 폴더는 건드리지 않습니다.** 서로의 기능을 연결하는 일은 ⑥ 합치기 단계에서 합니다.
- 구역 밖 파일을 고치면 AI가 저장을 멈추고 알려 줍니다.
- 프로젝트 규칙 폴더(`Harness/`, 루트 `Scripts/`, `.github/`, `Docs/Guides/`)는 PM만 고칩니다. 개인 MCP·Skill은 내 PC 전역에 설치합니다.

**습관 5가지**

1. AI에게 말하기 전에 **Unity에서 저장(Cmd+S / Ctrl+S)**부터 합니다.
2. **AI가 Unity를 조작하는 동안에는 Unity를 만지지 않습니다.**
3. 파일 이동·이름 변경은 **Unity 안에서만** 합니다. 탐색기에서 옮기면 `.meta`(파일끼리 연결해 두는 이름표)가 빠집니다.
4. Unity는 **Unity Hub에서 정해진 버전(6000.3.25f1)**으로 엽니다.
5. 마지막 확인은 **Play 버튼으로 직접** 합니다.

연습하고 싶으면 AI에게 "tests 브랜치 만들어줘"라고 하세요. `tests/*`는 망가뜨려도 되고 어디에도 합쳐지지 않습니다.

## 5. 브랜치 규칙

| 이름 | 용도 | 예시 |
|---|---|---|
| `feat/*` · `fix/*` · `refactor/*` | 새 기능 · 기능 수정 · 코드 정리 | `feat/curtain-open` |
| `resource/*` | 리소스만 추가 (아트·에셋 관리자, Task 없음) | `resource/character` |
| `integration/*` | 기능 묶음을 합치는 곳 (PM) | `integration/curtain-call` |
| `builds/*` | 빌드 버전 보관 (PM) | `builds/0.1.0` |
| `tests/*` | 연습장, 합치지 않음 | `tests/try-camera-shake` |

흐름은 한 방향입니다: 작업 브랜치 → `integration/*` → `dev` → `builds/*`. `dev`, `integration/*`, `builds/*`는 **PR로만** 합칩니다.

- `fix/*`, `resource/*`는 새 기능이 아니라서 순서를 건너뛰고 `dev`나 특정 `integration/*`로 바로 PR할 수 있습니다. `builds/*`로 바로 가는 것은 안 됩니다.
- `fix/*`는 보통 Task로 받지만 급한 문제는 Task 없이 바로 고칩니다. `resource/*`는 리소스 파일만 `Assets/Resources/`에 넣는 브랜치라 Task를 따로 만들지 않습니다. 코드·씬 수정이 필요하면 PM에게 Task를 요청합니다.

## 6. 이럴 땐 이렇게

| 상황 | 할 일 |
|---|---|
| "구역 밖 파일이라 저장하지 않았어요" | PM에게 "○○ 파일 수정이 필요해요" 요청 |
| "충돌이 났어요" | 직접 고치지 말고 PM에게 알림 |
| Unity에 빨간 오류 | "Console에 오류가 떠, 확인해줘" |
| "GitHub 연결이 안 돼요" | 웹페이지로 직접 올리기 또는 재시도 중 선택 ([연결 방법](github-setup.md)) |
| 크게 잘못된 것 같음 | 멈추고 PM에게 연락. 저장 기록으로 대부분 되돌릴 수 있습니다 |
