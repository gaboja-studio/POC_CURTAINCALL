# 다음 UI 적용 계획

현재 공연 HUD 적용을 기준으로 Start → Lobby → WaitingRoomBase 순서로 확장한다. 백스테이지·탈출로는 생성하지 않는다.

## 1. Start·Lobby 프리팹/기존 기능 대조
- Assets 내부의 완성 프리팹과 제작 Task·독립 테스트 씬을 먼저 확인한다. 전체 화면 프리팹이 없으면 준비된 버튼·패널을 조합할 수 있는지 확인하고 미제작 요소를 목록으로 남긴다.
- StartMenu 등 현재 방 생성/참가/나가기·연결 상태 흐름을 조사한다. UI 화면 목록 T1/T2/T3/L1과 연결점을 정리한다.
- 기존 CommonButtons/BasicPanels 등은 원본 규칙을 유지한다. LobbyHud는 이름만으로 로비용이라고 간주하지 않고 역할을 확인한다.

## 2. 공통 UI 문맥 확장과 화면 적용
- 공간 전환에도 공통으로 쓰는 알림/확인/설정 표시는 공통 UI 씬, 화면 전용 레이아웃은 Start/Lobby의 UI 루트에 둔다.
- 현재 CommonPerformanceUI는 공연 전용이므로 무조건 모든 씬에 띄우지 않는다. 재사용할 공통 계층과 공연 HUD 표시 조건을 분리한다.
- 방 생성/참가 버튼, 입력 검증, 연결 중/오류/취소, 참가자 명부·준비·호스트 시작 권한을 기존 세션 API와 연결한다.
- 인터랙티브 UI 적용 때 EventSystem/InputModule 중복·포커스·키보드/마우스 입력·커서 정책을 확인한다.

## 3. WaitingRoomBase
- 최신 dev의 실제 대기실 복귀·물리 출구 흐름 위에 W1/C4/C5/W6 대응 프리팹을 확인해 적용한다.
- 상호작용·구매·스케줄 화면은 구현된 데이터/API 범위 안에서 연결하며 게임 규칙과 경제 값을 UI에서 만들지 않는다.

## 4. 연결 검증과 완료 기준
- Start→Lobby→WaitingRoom→공연→WaitingRoom 실제 흐름, UI 씬1개/문맥 갱신/이벤트 해제 확인.
- 호스트·클라이언트 권한, 입장·퇴장·재접속, 실제 키 입력과 여러 해상도 검증.
- 기존 공연 HUD 회귀 및 아직 미실행인 2~4인 C3·불 접촉·관전 전환 검증.
- 각 단계마다 수정 파일·데이터 원천·실행 결과·미실행 항목과 Unity 확인 방법을 가이드에 갱신한다.
