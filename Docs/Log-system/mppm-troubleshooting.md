# MPPM 플레이가 대시보드에 안 보일 때

2026-10-22 Task-069. 02:42~02:45 KST 실제 사용자 MPPM 2인 플레이 제보.

## 확인된 현상

- TEST/0.1.0 화면은 총 플레이 0·이벤트 1·공연 0이었다. 필터는 이미 올바르게 선택돼 있었다.
- PC 큐에 144묶음·857개 사건이 남아 있었다. 해당 사용자 실행 2개 앱에 58묶음·485개 사건과 같은 runId가 존재했다.
- 외줄/대포 HOST 확정 실패, 스케줄 확정·준비 완료·D2T1 공간 관측이 있어 수집 전체가 중단된 상황은 아니었다.
- Editor.log에 저장 실패가 있었고 두 실행은 같은 senderId와 active.json을 썼다. 기존 큐는 동시 쓰기를 지원하지 않는다.
- 단독 PowerShell 및 UnityWebRequest의 동일 원문 POST는 HTTP 200·정상 ACK, ID/건수/SHA 일치. 격리 복사본 Acknowledge 성공, 사용자 원본 유지.
- Start 단독 재실행에서 실제 프레임 진행·RemoteConfigured true·LastError null과 대기 144→136을 관측했다. API 장애가 아니라 오래된 파일 우선 전송과 종료 시 전송 중단이 새 기록 도착을 지연시켰다.

## 수정

- 메인 큐는 그대로 유지하고 MPPM의 /Library/VP/ dataPath에만 clients/해시 큐·설치 ID를 부여한다. 같은 보조 프로젝트 재실행은 같은 큐를 복구한다.
- 성공 ACK 뒤 추가 1초 대기를 제거한다. 실패 재시도 간격과 ID/건수/SHA 확인은 유지한다.
- 현재 실행에서 생성한 묶음을 우선 전송한 뒤 과거 대기 묶음을 처리한다. 예전 검사 로그 때문에 새 플레이 표시가 수분씩 밀리는 것을 줄이며 과거 원문은 보존한다.
- LastUploadError를 일반 사건 수집 오류와 분리하고 PendingBatchCount·LastUploadAt 조회를 추가한다.
- Editor/개발 빌드 Console [Telemetry]에 수집 시작·로컬 저장/대기·Drive ACK·재시도를 표시한다. 인증값·원문은 출력하지 않는다.
- 기존 사용자의 대기 파일은 고치거나 합치지 않는다. 복구 전송도 같은 ID/원문을 사용하며 원본은 삭제하지 않는다.

- Console에서 대기 0 확인 → 대시보드 TEST/0.1.0 지금 갱신 → 세션 ID 선택으로 공연 2개·스케줄/준비를 확인한다.
- 이미 충돌 중 누락된 순간은 추측해 복원하지 않는다. 이번 복구는 디스크에 남은 사건만 대상으로 한다.
