# 대시보드 갱신·캐시

- 접속·로그인·필터 변경: getDashboard가 마지막 완료 스냅샷만 읽는다. 적재·통계 게시·원본 정리를 실행하지 않는다.
- 수동/30분 자동 갱신: 전체 사용자·환경·버전에 공통인 완료 후 5분 제한. 진행 중이면 이전 결과를 반환한다. 첫 캐시가 없으면 집계 대기 상태를 표시한다.
- 수신 원본은 LIVE 검색 결과를 먼저 읽고 전체 폴더를 다시 확인한다. 검색 색인 지연·검색 실패에도 전체 확인에서 누락을 막는다. 한 번 최대 100묶음/180초 제한은 유지하고 Events·Batches 쓰기는 25묶음씩 처리한다. 밀린 파일이 상한보다 많으면 다음 갱신에서 이어서 적재한다.
- Events 수신 공간의 방어 상한은 200,000건이다. 50,000행 초과 시 세션 상세 저장본과 일치한 행만 Drive로 옮긴다. LIVE 30일·TEST 7일 이후에는 세션 요약을 남기고 상세를 정리한다. [보관·증분 갱신](session-retention.md).
- 로그 적재 오류가 나더라도 현재 적재된 기록으로 설문 동기화·통계·캐시를 게시한다. 일부 적재 지연은 별도 안내하고 진단에 원인 코드를 남긴다. 시트·Drive·실행 시간에 한도가 있으므로 무제한 운영을 보장하지 않는다.
- 갱신 작업은 owner UserLock으로 직렬화하고 ScriptLock은 시작 결정·완료 포인터 교체에만 짧게 사용한다. 로그 수신은 기존 ScriptLock으로 배치 중복을 막으므로 긴 통계 계산과 겹쳐도 수신할 수 있다.
- Script Properties의 진행 임대는 7분에 만료된다. 실행 중단 시 다음 적격 요청이 복구한다. 실패 후 재시도도 최소 5분 간격이며 이전 완료 포인터는 유지한다.
- 원본 JSON 폴더 안의 비공개 ‘대시보드 캐시’ 폴더에 환경·버전별 원천/기본 화면과 인덱스를 불변 JSON으로 쓴다. 모두 저장한 뒤 완료 포인터를 교체하므로 미완성 파일은 조회하지 않는다.
- CacheService에는 파일·조회 결과를 20,000자 단위로 나눠 최대 6시간 보관한다. 용량 초과·부분 소실 시 Drive로 되돌아간다. 사용자 인증은 캐시 조회 전 매번 확인하고 viewer/auth를 공용 캐시에 넣지 않는다.
- 현재·직전 캐시 세대만 유지하고 더 오래된 캐시 파일은 휴지통으로 보낸다. 원본 로그 파일과 시트는 이 정리에 포함하지 않는다.
- 관리자 삭제는 갱신과 직렬화한다. 논리 삭제 적용 전 epoch를 바꿔 과거 화면 캐시를 차단하고 남은 기록으로 캐시를 다시 만든다. 이 재생성은 새 로그 적재가 아니며 직전 실제 갱신 시각을 유지한다. 정리가 실패해도 과거 캐시로 삭제 기록을 다시 노출하지 않는다.
- 화면은 15초마다 상태만 읽어 다른 사용자의 갱신 중 버튼을 비활성화하고, 완료 revision이 바뀌면 새 캐시를 읽는다. 브라우저의 주기 작업은 집계를 시작하지 않는다.

## 배포·첫 실행

prepare-deployment.cjs는 refresh-cache.gs도 결합한다. 기존 대시보드 배포를 새 버전으로 갱신하고 편집기를 새 소스로 유지한다. 기존 수신 URL·토큰·공개 범위·30분 트리거는 유지한다.
소유자가 scheduledRefresh를 한 번 실행해 첫 스냅샷을 만든다. 첫 캐시가 없을 때 일반 접속은 자동 집계를 하지 않는다.
캐시 형식만 다시 만들 때는 소유자가 rebuildDashboardCache를 실행한다. 새 원본을 적재하지 않고 기존 실제 완료 시각을 유지한다. checkDashboardCache는 기본 TEST/LIVE 건수·완료/다음 갱신 시각만 실행 로그에 출력한다(사용자 식별자·토큰 출력 없음).
실패 조사 시 diagnoseDashboardRefresh는 동일한 5분 제한을 지켜 갱신을 요청하고 마지막 실패 단계·허용된 오류 코드만 출력한다. 알 수 없는 예외는 REFRESH_ERROR로 가리며 원문·토큰·플레이어 정보는 기록하지 않는다.
