# CURTAIN CALL — Unity 씬 적용 인계

기준 시점: **2026-10-20 · 타이틀 v1 전달 직후**  
문서 버전: **1.0.0**  
목적: 리소스 제작과 실제 Unity 씬 적용을 두 채팅에서 병행한다.

## 1. 두 채팅의 담당 범위

| 구분 | 이 리소스 제작 채팅 | 새 Unity 씬 적용 채팅 |
|---|---|---|
| 주요 산출물 | PNG 레이어, 시트, 상태별 그림, 색·크기·9-slice, 리소스별 조립 도구, 누적 목록 | 씬별 화면 배치, Prefab/Hierarchy, 프로젝트 연결 코드, 입력·상태·이벤트 처리, 실제 적용 가이드 |
| 유지 책임 | 확정 C안, 원본 그래픽, 그래픽 메타데이터, 묶음별 버전 | 실제 프로젝트의 씬·Canvas·게임 데이터와 연결, 적용 상태 기록 |
| 검토 단위 | 기존처럼 한 묶음씩 사용자 피드백 | 준비된 씬/상태부터 하나씩 실제 적용·확인 |
| 변경 요청 | 적용 중 드러난 그래픽 문제를 받아 수정본 배포 | 필요한 새 그림·크기 변경·상태 누락을 제작 채팅에 전달 |

두 채팅 사이의 자동 동기화를 전제로 하지 않는다. 사용자 또는 작업 담당자가 새 묶음 ZIP과 `ART_RELEASE_NOTE.md`를 적용 채팅에 전달하고, 적용 결과나 수정 요청을 제작 채팅으로 가져오는 방식이다.

## 2. 현재 상태 — 그래픽 전달과 엔진 적용을 구분

- 이전 15개 묶음: **고유 PNG 137개 확정**.
- 직전 타이틀 T1/T2/T3 묶음: **신규 8개 + 기존 재사용 15개 = 패키지 포함 23개**.
- 누적 고유 PNG: **145개**, 이 중 타이틀 신규 8개는 사용자 피드백 대기.
- PNG 수는 씬 적용의 완료율이 아니다. Unity 임포트·컴파일·Play Mode·기기 검증은 모두 **미실행**으로 기록되어 있다.
- 타이틀 ZIP은 해당 23개 리소스 패키지다. 누적 145개 전체를 담은 ZIP이 아니다.
- 이 인계 ZIP에는 문서와 **첫 공연 HUD 적용용 기존 배포 ZIP 두 개**가 들어 있다. 나머지 묶음은 파일 목록을 참조해 씬별로 가져온다.

아트가 확정되어도 실제 네트워크, 게임 상태, 입력, 씬 로드가 연결된 것으로 간주하지 않는다. 반대로 모든 후속 그래픽이 완성될 때까지 준비된 공연 HUD 적용을 기다릴 필요도 없다.

## 3. 게임과 미학의 확정 맥락

2–4인 온라인 협동 공포 서커스 게임이다. 버려진 서커스의 단원이 되어 3일 동안 외줄타기·인간대포 같은 위험한 공연으로 돈을 벌고, 쉬는 시간에는 백스테이지를 탐색해 탈출한다. 관객은 위험과 고통을 좋아하고 안전한 플레이에는 야유한다.

감정은 욕심과 공포, 아슬아슬함, 친구 사이의 사고, 긴장 뒤의 숨 돌리기다. 붉은 커튼·따뜻한 텅스텐 조명·어두운 무대·낡은 나무와 천과 놋쇠가 배경이며 캐릭터는 단순한 로우폴리 스타일이다. 사용자 사물은 SYNTY POLYGON Apocalypse Pack을 많이 사용한다는 맥락을 따른다. 외부 팩 자체는 이 인계물에 포함되지 않는다.

선택된 스타일은 **C안 「무대감독 계기판」**이다. 작고 얇은 판, 절제된 금속 테두리, 제한적인 서커스 장식으로 핵심 정보를 읽게 한다.

반드시 유지할 규칙:

1. 핵심 정보 외의 요소가 상시 화면을 가리지 않게 한다. 상시 HUD는 작게 가장자리에 배치한다.
2. 공연 상시 HUD는 C1·C2·C3, 쉬는 시간 상시 HUD는 W1·C4다.
3. 메뉴를 열어도 멀티플레이 게임은 계속 진행된다. UI가 게임 시간을 임의로 멈추지 않는다.
4. 전체 화면 딤은 타이틀·로비에만 허용한다. 공연·대기실의 ESC, 확인창, 구매 패널에 전면 딤을 추가하지 않는다.
5. 상단 240 UI px의 핵심 HUD 영역을 보호한다. 플레이 중 호출 패널의 위쪽은 원칙적으로 y≥256 UI px에 둔다.
6. 부상 정보는 캐릭터 모습으로 보여준다. 별도 부상·체력 HUD를 추가하지 않는다.
7. 이미지에는 글자를 굽지 않는다. 제목 로고 CURTAIN CALL만 예외이며 숫자·키·한글은 TMP가 그린다.
8. 같은 유형은 같은 그림과 규격을 재사용한다. 씬마다 새 프레임을 다시 그리지 않는다.

**주의:** 원형 보존된 `style_contract_v1.json`에는 초기 상태인 `awaiting_step_2_confirmation`, `not_generated`, `planned_not_generated`가 남아 있다. 이 필드로 현재 완료 상태를 판단하면 안 된다. 현재 상태는 최신 누적 목록과 프로젝트 상태 파일을 우선한다. 과거 묶음의 당시 검토 대기 표기도 같은 원칙으로 해석한다.

기존 문서의 `/workspace/...` 경로는 제작 당시 작업 공간 경로다. 다른 채팅이나 사용자의 PC에서 같은 절대 경로가 존재한다고 가정하지 않는다. Unity 안에서는 `Assets/CurtainCallUI/...` 상대 경로를 사용한다. 새 채팅은 첨부된 ZIP을 실제로 열어 확인해야 한다.

## 6. 첫 적용: 공연 C1·C2·C3·P1

첫 순서를 공연으로 정한 것은 이번 병행 작업을 위한 제안이다. 그래픽 승인 상태를 변경하는 결정이 아니다.

`Packages/curtaincall_c1_v1.zip`과 `Packages/curtaincall_performance_hud_v1.zip`을 각각 풀어 `Assets/CurtainCallUI/` 아래 내용을 같은 프로젝트 경로에 병합한다. 기존 `.meta`를 보존하고 공용 클래스·에셋을 별도 경로에 중복 복사하지 않는다. 기존 파일이 서로 다른 버전이면 무조건 덮어쓰지 말고 해당 묶음의 의존성과 변경 내역부터 비교한다.

첫 두 ZIP에는 다음 조립 도구·View 코드가 있다. 실제 공개 메서드와 이벤트 이름은 원본 코드를 읽어 사용한다.

- C1: `CheerGaugeBuilder.cs`, `CheerGaugeView.cs`, `Docs/c1_assembly.json`.
- 공연 HUD: `PerformanceHUDBuilder.cs`, `PerformanceHUDView.cs`, `PerformanceProgressView.cs`, `PerformanceTimerView.cs`, `TightropeBalanceView.cs`, `Docs/hud_assembly.json`.

### 확정 기준 좌표

아래는 화면 좌상단의 절대 x/y가 아니라 **RectTransform anchor/pivot 기준 anchoredPosition**이다. 크기는 UI 단위이며 @2x PNG 크기와 구분한다.

| UI | 크기 | Anchor / Pivot | Anchored Position | 노출 |
|---|---|---|---|---|
| C1 팀 호응 | 192×208 | (0.5,1) / (0.5,1) | (0,-24) | 공연 상시 |
| C2 남은 시간 | 160×56 | (0,1) / (0,1) | (48,-40) | 공연 상시 |
| C3 진행도 | 408×76 | (1,1) / (1,1) | (-48,-40) | 공연 상시 |
| P1 균형 | 544×80 | (0.5,0) / (0.5,0) | (0,160) | 외줄 위에서만 |

C1은 단원별 점수 0–100이 링 둘레를 시계 방향으로 이어 채운다. 단원마다 고정 사분면을 배정하지 않는다. 공연 시작 참가자 수 N을 기준으로 권위 있는 최대값 N×100을 전달하며, 보통의 추락만으로 생존자 수 기준 최대값을 다시 계산하지 않는다. 접속 이탈 시 최대값 변경은 미정 정책 Q6이다.

`fill_i = clamp(score_i,0,100) / capacity`이고 시작 회전은 앞 단원 점수 누적분에 따른다. capacity≤0이면 채움을 숨긴다. 추락 강조는 사건 직전 구간을 시각적으로 표시하며 실제 점수 변경은 게임 데이터가 결정한다. 자세한 회전·레이어 구현은 C1 원본 조립 코드가 기준이다.

첫 통합에서 게임 데이터로 연결할 값은 단원 순서/ID/색/점수/추락 사건, 남은 시간, 경로 길이·단원 위치·추격 불·도착/최대 도달 위치, 로컬 외줄 상태·균형값·위험 체류량이다. 값의 단위·권위·갱신 주기를 실제 프로젝트에서 확인한다. UI 자체가 점수나 네트워크 게임 상태를 결정하지 않게 한다.

## 7. 월드 라벨의 사용자 확정 사항

| 종류 | 확정 용도 |
|---|---|
| 나무 표지판 / 천 배너 / 종이 쪽지 | 실제 물리 소품 표면처럼 보이는 재질형 리소스 |
| 기물 이름표 / 선반 칸 번호표 | 가까이 가면 나타나는 정보 UI |

월드 라벨은 **v2**가 기준이다. 다섯 종류를 모두 같은 상시 빌보드로 만들지 않는다. 근접 정보의 진입·이탈 거리, 가림, 동시에 보이는 개수, 로컬 관찰자 기준은 게임 연결에서 정한다. 묶음 UI ID는 L2/L3/H1/W4/W5이며 각각을 특정 재질에 임의 대응시키지 않는다.

## 8. 타이틀은 병행 연결 가능하되 검토 상태 유지

현재 타이틀 패키지 23개와 코드로 T1 메뉴·T2 방 코드·T3 LAN을 조립할 수 있다. 신규 그림 8개는 피드백 대기 상태로 유지한다.

- 에디터 메뉴: `Tools > Curtain Call UI > 타이틀 메뉴 만들기`.
- Pretendard 세 굵기의 TMP 폰트를 준비하고 PNG 검사 후 임포트·레이어 조립을 실행한다.
- 런타임 초기 상태는 Hidden, 타이틀 진입에서 `ShowMain()`을 호출한다.
- `ShowRoomCode()`, `ShowLan()`, `Hide()`, `Back()`, `SetFormBusy(bool)`, `SetFeedback(string,bool)`를 제공한다.
- 요청 이벤트: `CreateRoomRequested`, `JoinRoomRequested(string)`, `LanConnectRequested(string)`, `SettingsRequested`, `QuitRequested`, `FormClosed`.
- 네트워크 요청은 프로젝트에서 연결한다. 성공 시 Hide, 실패 시 피드백과 busy 해제. 늦은 응답은 `FormVersion`과 현재 모드를 확인한다.
- 방 코드 형식·LAN 주소 규칙은 아직 강제하지 않았다. 예시 문자열을 실제 검증 규칙으로 오해하지 않는다.
- EventSystem/InputModule을 자동 생성하지 않는다. 씬 로드·게임 종료·timeScale·커서 정책은 호출자가 소유한다.

전체 사용법은 `Baseline/title_unity_setup.md`를 따른다. 타이틀 패키지의 PNG는 이 인계 ZIP에 포함되지 않으며 정확한 파일명은 묶음 목록에 있다.

## 9. 아직 만들어야 할 그림

다음 리소스 제작 묶음은 **C14 설정 창과 필요한 공용 탭·슬라이더·토글**이다. 이후 W2 수화기 구매·판매, W3 스케줄표, C12 결과 패널, 단계 5 최종 화면 7개가 남는다. 입력 필드는 이미 타이틀 묶음에서 제작했으므로 다시 미제작으로 분류하지 않는다.

묶음별 검토 목업과 단계 5의 최종 통합 7화면은 구분한다. 최종 7화면은 공연/동료 추락/대기실/구매 패널/대성공/ESC+나가기 확인/반쯤 닫힌 커튼이다. 실제 씬 작업 결과가 확보되면 최종 시각 확인에 활용할 수 있지만, 아직 완료로 기록하지 않는다.

## 10. 실제 프로젝트를 볼 때 확인할 사항

Unity 버전, uGUI/TMP 및 기타 패키지 버전, 렌더 파이프라인, 입력 모듈, 네트워크 방식, 실제 씬 이름과 로드 방식, 기존 Canvas/Prefab, TMP 폰트, 게임 상태·타이머·점수·상호작용 클래스, 목표 해상도를 먼저 확인한다. 이 인계 문서에는 해당 프로젝트 파일이 없으므로 확인되지 않은 내용을 임의로 확정하지 않는다.

모든 것을 묻고 기다릴 필요는 없다. 확보된 파일로 기준 화면과 연결 표를 먼저 작성하고, 미확정 항목은 프로젝트 연결용 설정/어댑터 경계로 남긴다. 실제 코드 접근이 없으면 수정했다고 말하지 않고 적용 지침과 필요한 코드 파일 범위를 정확히 전달한다.

남은 게임 정책: 메뉴 입력(Q1), 방장 이탈(Q2), 소지 슬롯 수(Q3), 최초 가이드 범위(Q4), C6/C15 노출 방식(Q5), 접속 이탈 후 호응 최대값(Q6), 관전 전환/대상 없음(Q7), 씬 전환·전원 준비·실패·입력·Canvas 수명(Q8), 타이틀 접속/종료/입력 모듈(Q9).

## 11. 씬 적용 완료의 기록 기준

리소스 버전 확인 → Prefab/Hierarchy 배치 → 게임 값·이벤트 연결 → 실제 프로젝트 컴파일 → Play Mode → 필요한 화면비/입력/네트워크 상태 확인을 구분해서 기록한다. 아직 실행하지 않은 항목은 `not_run`으로 남긴다.

다른 채팅의 진행 결과는 `Templates/SCENE_PROGRESS.md`, 그래픽 변경 요청은 `Templates/ASSET_CHANGE_REQUEST.md` 형식으로 이 제작 채팅에 전달한다. 리소스 제작자는 다음 묶음마다 `Templates/ART_RELEASE_NOTE.md` 형식의 적용 변경 요약을 함께 제공한다.
