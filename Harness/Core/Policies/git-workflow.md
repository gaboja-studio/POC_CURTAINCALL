# Git Workflow

2026-10-27: 작업별 브랜치는 유지하고 업로드·내려받기 계층은 강제하지 않는다.

| 브랜치 | 용도 |
|---|---|
| dev | 팀 공용 원본. PR과 지정 팀원 검토 후 반영 |
| feat/* | 기능 추가 |
| fix/* | 버그 수정. 긴급 여부와 관계없이 직접 dev에 제출 가능 |
| refactor/* | 코드·도구 정리 |
| resource/* | 에셋 작업 |
| integration/* | 필요할 때만 사용하는 기능 묶음 |
| builds/* | dev의 빌드 버전 보관 |
| tests/* | 임시 실험. 정식 제출은 목적에 맞는 브랜치로 |

## 공유와 병합

- feat/fix/refactor/resource는 dev 또는 필요한 작업·통합 브랜치로 직접 PR할 수 있다.
- integration은 선택 사항이다. 다른 integration·작업 브랜치 변경도 dev를 기다리지 않고 받을 수 있다.
- 필요한 브랜치에서 직접 fetch/merge/pull할 수 있다. 받는 브랜치와 변경 방향을 먼저 확인한다.
- **dev를 바꾸는 경로는 PR 1회와 지정 팀원 검토**를 유지한다. 병합은 PM만의 일이 아니며 저장소 권한을 따른다.
- dev 이외의 작업·통합 브랜치 공유는 PR을 필수로 요구하지 않는다. force·reset·다른 사람 변경 덮어쓰기는 별도 명시 요청 없이는 하지 않는다.
- builds는 dev에서만 받는다. dev에 실험 중인 변경을 역으로 끌어들이지 않도록 대상 방향을 확인한다.
- 완성된 작업을 dev로 올릴 때는 Squash, 계속 공유할 통합·동기화는 Merge commit을 기본으로 한다.
- Squash 병합한 작업 브랜치는 후속 작업에 재사용하지 않는다. 새 브랜치를 만든다.
- 충돌은 담당자끼리 해결한다. AI는 씬·프리팹 YAML 충돌을 임의로 합치지 않는다.

## 시작과 기록

- 목적을 나타내는 소문자 kebab-case 이름을 쓴다. 현재 프로젝트의 feat/fix/refactor/resource/integration 이름을 유지한다.
- plan의 Branch로 Task를 찾는다. Base는 공유 대상 제안이며 독점 소속·작업 허가가 아니다. 기본값은 dev.
- `new-task`는 3문서를 만들며 브랜치를 만들거나 저장·push하지 않는다. `start-work`가 기존 또는 선택 기준 브랜치에서 작업 브랜치를 연다.
- `sync-integration`은 선택한 출발·대상 브랜치의 PR을 만드는 호환 도구다. 부모/자식·PM 승인 단계는 없다.

## 저장과 안전

- AI는 사용자가 저장·제출을 요청할 때만 commit/push한다. 실제 명령 실행이 저장·제출 요청인 경우도 포함한다.
- 저장은 현재 변경을 확인하고 필요한 가벼운 검사를 한다. Unity 변경이 없으면 에디터 연결을 요구하지 않는다. 자동 테스트는 묶음 완료나 요청 시 선택한다.
- 커밋 작성자는 gh 로그인 계정만. AI 작성자·Co-Authored-By·Generated with 줄을 넣지 않는다.
- 비밀값·개인 설정·Library는 추적하지 않는다. 외부 에셋은 `_ThirdParty` private 저장소, Unity 에셋은 `.meta`와 함께 보존한다.
- 저장소 보호 설정은 파일 수정만으로 바뀌지 않는다. 실제 원격 제한이 남으면 정확히 보고한다.
