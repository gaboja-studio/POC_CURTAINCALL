# 기능과 네트워크 동기화를 같이 만든다

## 언제 읽나

외줄·목마·도구 같은 게임 기능 Task를 계획·구현하거나, 네트워크 코드를 다른 기능에서 써도 되는지 판단할 때.

## 결정

- 2026-10-02 / PM(@MoHoDu):
  1. **007(플레이어 동기화)을 먼저** 한다. 테스트 캡슐이 아니라 **004 실제 플레이어 프리팹**에 동기화 기반을 만든다: 내 캐릭터만 내 입력을 받기(소유권), 위치·자세·점프 공유, 호스트 판정 요청·결과 공유, 상태(사망 등) 공유, UI가 내 캐릭터를 따르기.
  2. 007 이후의 기능 Task(005·011·006·008)는 **기능 구현과 동기화를 같이** 한다. 단계마다 여러 명 접속(Multiplayer Play Mode)으로 확인한다.
  3. 이후 Task는 **007의 공개 기능(`Assets/Scripts/Network/PlayerSync/`)과 004 공개 함수를 직접 써도 된다.** 엔진 정책 `code-folders.md`의 "기능 연결은 연결 Task에서만"보다 이 결정이 우선한다(Project > Engine). 공개 진입점만 쓰고 내부 클래스는 쓰지 않는다.
  4. 007 공개 기능을 고치거나 넓혀야 하면 그 Task `setup.md`에 경로를 배정받는다(한 번에 한 Task만 수정).
  5. 009는 **4인 외줄 코스 최종 씬과 남은 연결**, 010은 **목마 온라인 예외(동시 시도·목마 중 추락 등) 정리**로 줄인다.
- 권한 원칙은 [멀티플레이 구성](multiplayer-stack.md) 그대로다: 이동은 각자, 판정(사망·목마·게임 진행)은 호스트.

## 이유

혼자 기준으로 만든 기능은 4명이 되면 고칠 곳이 생긴다(모든 캐릭터가 내 키에 반응, UI가 엉뚱한 캐릭터 표시, 판정이 사람마다 다름). 동기화 규칙을 먼저 정하고 기능을 처음부터 그 규칙대로 만들면 같은 기능을 두 번 손대지 않고, 온라인 문제를 5일차가 아니라 만드는 자리에서 찾는다. 작업을 한 사람이 순서대로 하므로 병렬 격리의 이점이 작다.

## 바꾸려면

PM 결정이 필요하다. 통합 `plan.md`·`meta.md`, 관련 Task 문서, 이 파일을 함께 고친다.
