# 플레이어 조작 구조

## 언제 읽나

플레이어 입력·조작을 추가하거나, 새 콘텐츠(묘기)에서 키 동작을 다르게 만들거나, 외줄·목마 기능을 플레이어에 붙일 때.

## 결정

- 2026-10-02 / PM(@MoHoDu): 콘텐츠마다 키의 동작이 바뀔 수 있으므로 조작을 세 층으로 나눈다.
  1. **입력** — 키를 키맵핑 문서의 "공통 역할"(이동, 자세 제어, 기본 액션, 좌우 보조 방향, 상호작용)로 읽는다. 키 변경은 입력 에셋(`Assets/Resources/Input/PlayerControls.inputactions`)에서 하며 코드를 고치지 않는다. 짧게/길게·홀드 판정도 이 층에서 한다. (`PlayerInputReader` → `PlayerInputFrame`)
  2. **조작 규칙(전략 패턴)** — 콘텐츠마다 규칙 하나(`PlayerControlScheme` 상속, ScriptableObject)를 만든다. 공통 역할이 그 콘텐츠에서 무슨 뜻인지, 상황(목마 중 등)에 따라 무엇을 할지 정하고 동작 부품을 부른다. 콘텐츠가 `PlayerController.SetScheme`으로 갈아 끼운다. 외줄: `TightropeControlScheme`.
  3. **동작 부품** — 이동·점프(`PlayerMover`), 균형(`PlayerBalance`) 등. 키도 콘텐츠도 모르고 공개 함수(`SetMoveInput`, `RequestJump`, `SetCorrectionInput` …)로만 움직인다.
- 동작 부품은 입력을 직접 읽지 않는다. 입력은 한 프레임만 유효하며 조작 규칙이 매 프레임 넣는다.
- 키 배치 자체가 완전히 다른 콘텐츠가 생기면 그때 입력 맵을 추가해 전환한다(지금은 만들지 않음).

## 이유

키 변경은 데이터(입력 에셋)로 충분하지만, 같은 키가 상황에 따라 다른 일을 하는 것(혼자 점프 / 목마 분리 점프 / Q+Space 옆줄)은 코드 규칙이 필요하다. 둘을 나누면 키를 바꿀 때 개발자가 필요 없고, 새 콘텐츠는 기존 규칙을 건드리지 않고 규칙 하나만 추가한다.
