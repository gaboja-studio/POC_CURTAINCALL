# MPPM 캐릭터 분홍색과 메모리 부족

## 언제 읽나

대기실과 탈출로를 함께 로드한 실제 4인 에디터 테스트에서 캐릭터가 분홍색으로 보이거나 씬 재로드 후 클라이언트가 끊길 때.

## 확인된 현상

- 16GB 메모리 환경의 메인+보조 에디터 3개 실행 중 Player 2 로그에 `BluePierrot Paper`와 `Bear Paper` 셰이더 컴파일 `out of memory`가 기록됐다. 셰이더 컴파일러 연결 해제와 HLSL 파싱 오류가 함께 발생했다.
- 클라이언트별 `Library/VP/<id>/Logs/Editor.log`를 확인한다. 다른 에디터에서 정상으로 보이는 것만으로 문제 클라이언트가 복구됐다고 판단하지 않는다.
- 보조 에디터 종료 후 메인에서 해당 재질의 패스를 동기 재컴파일했을 때 곰·파란 삐에로·분홍 소녀·토끼·URP Lit 모두 오류 없이 지원됨을 확인했다. 이 결과는 실제 4인 화면 복구 확인과 구분한다.
- 최종4인 실행에서도 한 클라이언트의 PinkGirl/BluePierrot 오류가 재발했다. 해당 클라이언트에서 캐릭터4종 패스를 순차 재컴파일한 후 오류0을 확인하고 실제 곰·파란 캐릭터 화면을 정상 확인했다. 낮춘 프리뷰 품질과 현재 화면 복구는 원래 품질 반복 실행 안정성의 보장이 아니다.

## 대응

1. 게임/캐릭터 원본을 교체하기 전에 실패 로그와 메모리 여유를 확인한다.
2. 검증용 에디터를 정상 중지하고 실패한 셰이더를 다시 컴파일한다.
3. 네 에디터를 다시 시험할 때 임시 텍스처 품질 조절이 필요하면 원래 설정을 백업하고 시험 후 복구한다. `BeforeSceneLoad`에서만 낮추면 에디터 최초 씬 읽기의 메모리 최고치를 피하지 못할 수 있다.
4. 실제 네 클라이언트의 화면·연결·로그를 확인한 후에만 해결로 기록한다. 정적 셰이더 검사만으로 플레이 테스트 통과라고 쓰지 않는다.

## 컴파일 부하와 텍스처 메모리 (2026-10-31)

- Paper 셰이더의 `Drops` 중첩 3×3 `[unroll]`과 반복되는 noise 식이 컴파일 작업을 크게 펼쳤다. bounded `[loop]`와 반복 불변 noise 분리 뒤 메인에서4종 패스가 약1.4초씩 컴파일됐으며, 최종 판정은4개 에디터의 실제 변형/화면으로 한다.
- 새 Editor.log에 OOM이 없어도 `ShaderUtil.GetShaderMessages`에는 이전 실패가 남아 있을 수 있다. 기존 메시지를 기록하고 해당 셰이더의 캐시/메시지를 지운 뒤 실제 재질 패스를 재컴파일해 현재 오류와 과거 오류를 구분한다. 오류 목록만 지우고 해결이라고 판단하지 않는다.
- W+A 원래 비스트리밍 상태에서 각 에디터의 `Texture.currentTextureMemory`는 약814~828MB였다. 8192² 정적 한글 폰트2개는 각134MB native 크기이며 공용 UI의 정적 아틀라스 규격이 있으므로 임의 Dynamic 전환 대상이 아니다.
- PC 품질의 텍스처 스트리밍과 실제 W/A 3D 재질이 참조하는 큰 텍스처의 importer streaming을 함께 켠다. 에디터 CPU on-demand 로딩은 Unity6000.3.25f1/DX12에서 렌더 패스 중 업로드 메모리 해제 오류를 유발해 원래false로 복구했다. 단순히 메모리를 줄이려는 목적으로 켜지 않는다. 원본 해상도/압축/UI 폰트와 플레이 품질 mip limit은 보존한다.
- 4에디터 실행 중 idle import worker가 수GB를 추가 점유했다. 대기실/A의 Play 시작 때 DesiredWorkerCount를0으로 줄이고 Play 종료 때 SessionState에 저장한 원래 값을 복구한다. 가상 클라이언트나 일반 앱을 임의 종료해 메모리를 확보하지 않는다.

## 진입 지연 측정 시 구분

- 셰이더 오류0과 캐릭터 정상 화면은 진입 프레임 개선의 증거가 아니다. 반복4인 실행에서 셰이더는 정상이지만 출발 활성화가0.3~3.3초로 달라졌다. 새 에디터 반복에서도 따로 측정한다.
- `Texture.currentTextureMemory` 감소를 전체 시스템 RAM 감소율로 표현하지 않는다. 스트리밍 후 약376~383MB였지만4에디터의 private commit은 프로세스당 수GB였다. private commit과 실제 물리 메모리 점유도 구분한다.
- 비활성 사전 로드만으로 첫 활성화 비용까지 없어지지 않는다. W 정리는 캐시한 렌더러 목록을 분산 처리하고, A 배경은 기존 모듈 단위와 순수 정적 자식 단위로 나눠 초기화한다. 제어 스크립트가 있는 기믹 내부를 임의 분할하면 초기화 순서/참조를 깨뜨릴 수 있다.
- 실제4인 검사에서도 고정900ms 대기만으로 모든 원격 상태가 도착했다고 가정하면 안 된다. 출발 후 복제된 단계/카메라 상태를 제한시간 내 확인하고, 검사 파일 공유 경합은 게임 입력/네트워크 실패와 구분한다.
