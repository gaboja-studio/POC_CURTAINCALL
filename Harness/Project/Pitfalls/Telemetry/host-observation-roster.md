# 공연 참가자와 사건 기록을 분리한다

## 증상·원인
- 호스트 단독 업로드라도 사건 생성까지 호스트가 담당하는 것은 아니다. 기존 시작·구간·진행은 각 클라이언트의 로컬 관측과 전달에 의존했다.
- 공연 열림과 캐릭터 배치 완료 시점은 다르다. 시작 1회 발행이 준비보다 빠르면 기록이 빠지거나 이전 공간의 위치가 남는다.
- 도착한 사건만으로 참가자를 만들면 기록이 없는 참가자를 플레이하지 않은 사람으로 오인한다.

## 대처
- 공식 공연 명단을 PERFORMANCE_ROSTER로 먼저 저장한다. 시작·구간·진행·도착은 호스트가 플레이어별로 관측하고 저장 성공 후에만 완료 표시한다.
- 실제 배치를 확인한 뒤 시작 위치를 남긴다. 늦은 첫 사건으로만 참가를 확인했다면 START_NOT_OBSERVED로 표시하고 원래 시작 시각·좌표를 만들지 않는다.
- 타임라인의 명단과 사건 수를 분리한다. 같은 공연·플레이어의 신형 HOST_PLAYER 기록을 우선하되 구형 LOCAL 기록은 호스트 기록이 없을 때 유지한다.
- 표시 개수 축소 시 시작·사망·절단·추락·도착·퇴장은 보존한다. 과거에 수집하지 못한 사건은 복원할 수 없다.

## 확인·적용
- core/dashboard/session-store Node 검사, EventContractTests, Tightrope_PublicSettlement 전용 PlayMode로 확인한다. 4인 누락 표시는 합성 데이터이며 두 PC 검증과 구분한다.
- 수신 서버와 대시보드에 새 이벤트 계약을 먼저 배포한 뒤 새 게임 빌드를 배포한다. 구형 수신 서버는 새 이벤트가 포함된 배치를 거절할 수 있다.
