# 원격 플레이어 배치 전 호스트 판정

## 언제 읽나

게임 흐름으로 공연 씬에 들어갔을 때 호스트는 살아 있고 참가자만 시작부터 사망·실격일 때. 새 공연 씬에 위치 기반 호스트 판정(낙하선·영역 사망 등)을 추가할 때.

## 증상

2026-10-17 실제 2인: 줄타기 → 대기실 → 백스테이지 → 인간 대포에서 P2만 시작부터 Fallen, 맵 아래로 계속 낙하. 1인 LAN 자동 검사에서는 재현되지 않았다.

## 원인

- 중간 공간(더미)에는 바닥이 없어 몸이 계속 떨어진다.
- 출발점 이동은 소유자가 한다. 호스트 자신은 같은 프레임에 배치되지만 원격 소유자의 순간이동은 네트워크로 늦게 온다.
- 그 사이 HumanCannonRouteSystem이 호스트에 남은 원격의 옛 위치(-10m 아래)를 보고 ServerKill했다.

## 대처

연결 공연 Entry가 호스트에서 출발점 확인 전 사망을 거절한다(CampaignPerformanceEntry, 줄타기는 CampaignTightropeAdapter의 출발점 확인 후 시작). 새 공연을 연결할 때도 같은 대기 경계를 유지하고, 판정 코드에서 "씬 로드 = 모두 배치됨"으로 가정하지 않는다.

## 확인 방법

1. `RevivalTests/PerformanceEntryJudgeTests` PlayMode 실행(1인 LAN 합성).
2. 실제 2인으로 중간 공간을 거쳐 해당 공연에 들어가 참가자 생존·출발점을 확인한다. 1인 검사로 대체하지 않는다.

## 이동 중 장애물도 두 시각을 섞지 않는다

배치 이후에도 소유자 위치가 호스트에 늦게 도착한다. 호스트의 옛 위치를 현재 톱/불꽃에 대입하면 피해자가 피한 화면과 다른 결과가 나온다. 추격 포획·외줄 톱/불꽃·일반 대포 장애물·별도 대포 톱 관문/불꽃은 피해자가 현재 표시 접촉을 보고하고 호스트가 과거 형상·소유자·라운드/장치 회차·재시작·순서·유효 시각을 검증한 뒤 기존 피해 경로로 확정한다. 원격 host-only 피해를 다시 추가하지 않는다.

피해자의 현재 표시 판정에는 호스트 검증용 저주기 이력을 쓰지 않는다. 별도 톱 관문은 각 렌더 외형의 실제 틈도 유지한다. 접촉 재전송과 초기화 전 보고는 추가 절단을 만들면 안 된다. 관련 프로토콜 변경은 참가자 모두 같은 버전을 사용한다.

같은 씬 재호스팅처럼 서버 시각이 되감기면 형상 이력·다음 샘플 예약·수신 하한도 함께 버린다. 이전 세션의 큰 시각 때문에 새 형상 기록이 멈추지 않게 한다.

실제4프로세스 LAN 지연100ms/지터30ms/유실3% 및 자동 검사 근거와 한계는 [후속 검증](../../../Tasks/Active/Task-20261103-099-pursuit-network-perf/followup-verification-20261104.md)에 있다. 이 결과를4대PC/Relay나 사람의 경계 회피 검사로 대체하지 않는다.

## 리허설 소구간 전환에도 같은 경계가 필요함

2026-11-04 Task-20261102-097: 2인 MPPM에서 트리거 그네 시작 즉시 P2 도착·뒤로 이동 불가 보고. WaitingRoomRehearsal.HostJudgeStage는 회차별 배치 준비 확인 없이 이전 원격 위치로 도착자를 등록한다. 실제 설정 계산에서 2-2의 38~38.5m가 2-3에서는 35~35.5m가 되어 도착 허용 범위 [32,35.5]에 겹쳤다. arrived는 회차 동안 유지되고 TrackPersonalProgress가 도착선을 벗어나면 되돌리므로 출발 배치 후에도 도착점으로 붙잡힐 수 있다.

후속 수정은 회차별 배치 요청과 호스트 출발 좌표 대조로 도착 판정을 잠그고 승인 전 소유자의 이동을 대기시킨다. 합성 원격 배치 경합 및 기존 도착자 제한/투표 PlayMode 2건은 PASS, 실제 MPPM 2인 입력 재검증은 별도다. 회차별 소유자 배치와 호스트의 해당 위치 수신을 함께 확인해야 한다. 단순히 새 코스를 생성했거나 고정 시간을 기다렸다고 준비 완료로 간주하지 않는다.

## 대포 리허설 시작 낙사 (2026-11-05)
- 코스 생성 직후 Route의 낙하선은 대기실의 기존 위치보다 높다. 일반 공연 Entry를 거치지 않는 리허설에도 소유자별 배치 승인 경계가 필요하다.
- PracticeMode의 준비 predicate로 Route 낙사/개발 복귀와 ServerFallDeath를 보호한다. 미배치자를 fallen 집합에 먼저 기록하면 실제 첫 추락이 누락되므로 집합 추가 전에도 거른다.
- 합성 원격을 낙하선 아래에 둔 뒤 배치 요청→위치 수신 순서를 검사했다. 승인 전 사망 0회, 승인 뒤 실제 추락 1회 PASS. 실제 별도 클라이언트 검증과 구분한다.

## 공통 낙하 추적의 순간이동·부활 경계
- 순간이동 reset RPC가 실제 NetworkTransform 위치보다 먼저 도착할 수 있다. 목적지로 낙하 최고점만 초기화하면 다음 LateUpdate가 서버의 옛 높은 위치를 다시 최고점으로 기록한다.
- 목적지 pose 수신 전에는 transform 샘플만 보류한다. 정확한 목적지 프레임을 못 본 경우도 있으므로 현재 생명의 유효한 owner 최고점·지지면 착지 보고까지 막지 않는다. 착지 pose도 늦으면 보고된 feet를 새 대기 목적지로 삼는다.
- 재시작 번호만으로는 개인 부활 전 낙하 보고를 거를 수 없다. peak·teleport·landing·확인·신발 반동·일반 낙하 RPC에 부활 번호도 검증하고, 부활 콜백에서 추적·예약 낙하를 즉시 초기화한다. Normal이 번호보다 먼저 오면 이전 번호로 위치를 보낼 수 있으므로 새 번호 수신 후 소유자 위치를 다시 통지한다.
- 기물 비행의 서버 CompleteFall뿐 아니라 소유자 LandingMessage 수신도 추적을 끝내야 한다. 그렇지 않으면 동일 비행을 일반 낙하로 재보고한다. 이전 비행 revision/segment의 응답은 현재 낙하를 초기화하지 않는다.
- 관련 합성 재현은 Task-114의 TutorialFallTracking 검사. 실제 두 클라이언트 지연 플레이와 구분한다.
