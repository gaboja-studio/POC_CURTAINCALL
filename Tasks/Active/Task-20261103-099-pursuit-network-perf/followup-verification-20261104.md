# dev 통합 후 판정·성능 후속 검증

## 이번 변경

- dev `8b8910da`(통합 대기실 PR280 포함)를 현재 작업 브랜치에 충돌 없이 반영했다. 통합 커밋은 `c6da5ee6`이다.
- 인간 대포의 별도 톱 관문, 최종 톱, 추격 불꽃에도 피해자 접촉 보고를 연결했다. 호스트 복제 위치만으로 원격 참가자에게 피해를 주지 않는다. 호스트가 시각·소유자·재시작·장치 회차·좌표·접촉 형상을 검증한 뒤 기존 절단/사망 경로로 확정한다.
- 떨어져 있는 톱 사이의 빈틈을 하나의 큰 사각형으로 덮던 판정을 각각의 외형으로 나눴다. 피해자는 현재 보이는 톱으로 판단하고, 호스트는 30Hz/48칸 이력으로 보고 시각을 확인한다. 75ms 이내 이전 형상이 없으면 피해를 거절한다.
- 메시지는 reliable/sequence 방식이며 같은 접촉의 재전송은 중복 절단하지 않는다. 재시작/장치 초기화/씬 해제 시 기록을 지운다. 별도 시스템 메시지도 v2로 올려 혼용을 막았다. 모든 참가자가 같은 변경을 받아야 한다.
- 옛 수동 준비 F를 사용하던 구조/그네 검사는 현행 구조 장갑·자동 지원 규칙으로 바꿨다. 제품의 구조·착지 충격 수치는 바꾸지 않았다.
- 측정 도구는 '대기실 씬 설정'에서 고른 씬을 측정한다. 이제 통합 WaitingRoom이 기본 측정 대상이며 씬별 첫 로드 여부를 따로 기록한다.

## 실제 4인 지연 LAN

메인 Editor와 공식 MPPM 가상 플레이어3개, 실제 독립 프로세스4개를 LAN/UTP로 연결했다. 각 송신측 패킷 큐에 지연100ms·지터30ms·유실3%를 적용했다. 서로 다른 PC4대/Relay/출시 빌드 검사는 아니다. 좌표를 지정한 접촉 검사이며 사람의 키보드 회피 시험도 아니다.

각 조건90초 동안 모든 프레임에서4인 연결이 유지됐다. 클라이언트 RTT 중앙값은 톱262~269ms, 불꽃252~263ms였다. 유실로 인한 RTT 꼬리도 원본에 남겼다. 이 검사의 프레임 수치를 최적화 전후 개선률로 사용하지 않는다.

| 검사 | 안전한 피해자의 호스트 복제 위치만 접촉 | 피해자 실제 접촉 | 확정 결과 |
|---|---|---|---|
| 대포 톱 관문 | owner1 무부상 | owner3, 17:56:35.4408529Z | 17:56:35.5988349Z, 약158ms 뒤 왼다리1개 절단 |
| 대포 추격 불꽃 | owner1 Normal 유지 | owner2, 17:59:33.1683582Z | 17:59:33.3019399Z, 약134ms 뒤 Fallen |

톱은 지속 접촉 중 추가 절단 없이1회였고, 호스트와 피해자 양쪽에서 같은 부상/사망 상태를 확인했다. 불꽃의 발화 시각도 호스트/피해자에게 동일하게 전달됐다. 다른 참가자들의 기존 상태도 유지됐다. 원본8개 캡처는 [ZIP](Verification-20261104/cannon-network-raw.zip), 요약은 [JSON](Verification-20261104/obstacle-network-summary.json), 시작/확정 시각은 같은 폴더의 `gate-v2-*`, `fire-v2-*`에 보관했다.

위90초 검사는 최종 '피해자는 현재 형상, 호스트만 이력' 분리 직전 버전이다. 최종 코드에서도 같은4프로세스/100ms·30ms·3% 조건으로 `gate-final-v2`90초와 `gate-final-hold-v2`60초를 추가 실행했다. 모든 표본4인 연결 유지, 클라이언트 RTT 중앙값241~263ms. 안전한 owner1의 호스트 복제만 접촉시켜도 무부상, owner3 실제 접촉01:46:45.1659372Z→확정01:46:45.3526210Z(약187ms), 네 화면 상태 일치. 추가60초 전체 지연 지속 접촉에서도 모든 화면의 owner3 손실 부위는4(왼다리1개)로 일정했다. 끝에 현재 형상 contact=true도 확인했다. [원본8개ZIP](Verification-20261104/final-gate-network-raw.zip), [요약](Verification-20261104/final-gate-capture-summary.json), [화면별 상태](Verification-20261104/final-gate-peer-states.json)와 시작/확정/지속접촉 종료 시각을 보관했다.

가상 Editor의 Console에 MPPM 시작/자산 갱신 중 발생한 'Asset Database is set to Read Only' Assert2개가 남아 있어 Console 전체 오류0이라고 쓰지 않는다. 게임 접촉 이후 새 오류와 구분했다. 최초 재개 당시 Editor가 Start/정지 상태로 바뀐 것을 확인해 검증 씬/Play/4인 명부를 다시 확인한 뒤 측정했다.

앞서 적용한 비신뢰 위치 델타의 A→B→B→A 비교는 [기존 보고서](four-player-lan-report-20261104.md)에 있다(p95 위치 오차 약31% 감소, FPS 개선 근거 없음).

## 통합 대기실 측정

[측정 원본](Verification-20261104/unified-performance.json): 이 Editor 세션에서 통합 씬 첫 로드이며 OS/GPU 캐시를 지운 콜드 로드나 저사양 빌드 측정은 아니다. 로드3.42초, 초기화 준비4.55초, 측정 중 최장 프레임947ms. 해당 프레임의 GC.Collect 자기 비용328ms였다. 추격자26개 생성의 작업시간20.94ms/8프레임, 가장 긴 개별 생성8.13ms였다.

로비 단일 시점은7,232 batches/4,741 shadow casters로 가장 무거웠다. 추격 payload 추정은 상태4Hz+위치20Hz에서19.41KiB/s이며 NGO/UTP 헤더와 추가 상태 이벤트는 제외한다. 이를 실측 네트워크 대역폭이라고 쓰지 않는다.

## 렌더 후보: 적용하지 않음

임시 URP 파이프라인과 고정 카메라3개 시점으로 GPU Resident Drawer를 비교했다. 원본 렌더 에셋·씬은 저장하지 않았다. 카메라/품질 파이프라인/프레임 제한/배경 실행/셰이더 stripping 설정은 정상 종료·리로드 시 복원한다.

첫 A1→B1→B2→A2는 필수 BatchRendererGroup KeepAll 설정이 없어 후보가 비활성화됐다. 해당 `render-a*.json`/`render-b*.json`은 무효 비교로 보존한다. Unity 패키지의 `GPUResidentDrawer.Validator.cs`를 확인해 필수 설정과 실제 instance 활성 검사를 추가했다. 읽기 전용 API에 대입한 최초 도구 컴파일 실패는 GraphicsSettings SerializedObject 경로로 수정했다.

보완 후 `valid-b1`은 첫 셰이더 준비로 첫 방 표본이 없어 complete=false였으므로 전체 비교에서 제외한다. `valid-b2`는 실제 GPU instance 활성·세 방 표본을 확인했다. 도구는 이후 긴 셰이더 준비가 끝난 렌더 프레임부터3초씩 수집하도록 보완했다.

| 시점 | 기존 A1/A2 batches 평균 | 후보 B2 batches | 기존 A1/A2 프레임 중앙값 평균 | 후보 B2 중앙값 |
|---|---:|---:|---:|---:|
| 숙소 | 2,150 | 870 | 13.64ms | 13.50ms |
| 로비 | 6,322 | 1,455 | 14.21ms | 15.80ms |
| 연습실 | 4,570 | 543 | 13.61ms | 13.99ms |

그리기 요청은 줄지만 이 환경의 프레임 이득은 확인되지 않았다. 후보의 완전한 반복 표본도1개뿐이다. 첫 셰이더 준비 멈춤과 빌드 용량·메모리·4인/저사양 영향까지 확인하지 않고 기본 설정을 바꾸지 않는다. 추가 정적 배칭·그림자 축소도 아직 제품에 적용하지 않았다. [유효/불완전 원본 요약](Verification-20261104/render-valid-summary.json)에 표본 수와 complete/active를 함께 남겼다.

## 회귀 검증 상태

통합 대기실2/2, 매달리기/구조4/4, 그네2/2, 현행 장갑 지원1/1, 부상4단계 최종 비행1/1 통과. 최종 소유자 접촉7/7(대포 신규4개·외줄 기존2개·선택형 관문1개), 빠른 톱4/4 통과. 보고 시각300ms 지연·회피·중복·장치 회차/재시작 거부를 포함한다. 기존 일반 대포 장애물2개는 전체 대포 검사에서 통과했다.

선택형 수직·협동·해제 관문은 원본에서 비활성화된 상태를 유지하고 메모리 복사본에서만 유효 구간에 구성했다. 세 종류의300ms 지연 접촉/회피/중복 검사1/1 통과([결과](Verification-20261104/optional-saw-boundaries.json)). 최초 fixture의 정적 settings 접근, 기존1초 피해 간격, 현재 코스 밖의 옛158m 위치, 같은 프레임 중복 시각 샘플을 바로잡았다. 정상 Update가 새 형상을 기록한 뒤 보고 시각을 잡으며, 실제4인 경계 회피 통과를 뜻하지 않는다.

초기 대포 전체 회귀58개는41통과/15실패/2생략, 중간49통과/7실패/2생략, [최종 전체 실행](Verification-20261104/cannon-full-final.json)은 **55통과/1실패/2생략**이다. 옛 봉7개/삭제된 봉 톱/현행 비활성 톱 선택/과거 조작·수동 준비/리허설 전환/잘못 구성한 수신 객체·UI의 입력 리더 재등록 및 alpha0 진입 조건을 수정했다. 철망 위 비행도 최종 전체 실행에서 통과했다. 제품의 연속 반동/관성 보정·일정 난도·입력 중립 대기·C6 진입 애니메이션은 바꾸지 않았다.

남은 실패는 `AppliedMetalTransports_FitRoundLoadAndOpenBothVisualAndPhysicalDoors`다. 현재 운송판 반폭(2.75,2.00), 트램폴린 실제 반지름2.47534m, 손잡이 오프셋(-2.80,0,0)으로 중앙에 놓아도 손잡이/원형 외곽이 전부 들어가지 않는다.3개 운송판에서 같은 결과였으며 해당 씬·HumanCannonTransport.cs는 dev8b8910da와 diff0임을 확인했다. 이번 네트워크 수정에 배치 확대를 섞거나 기대값을 바꿔 통과시키지 않았다.2개 생략은 로컬 PracticeBot 실행 파일을 요구하는 검사다. **전체 통과나 머지 준비 완료로 보고하지 않는다.**

전체 실행 이후 검토에서 같은 씬 재호스팅의 서버 시각 초기화 경계를 추가 보완했다. 시각이 뒤로 가면 이전 형상·샘플 예약·수신 하한을 정리하고 새 형상을 즉시 기록한다. 해당 Gate 회귀를 [개별1/1 재실행](Verification-20261104/gate-clock-restart.json)해1000초→1초 합성 시각에서 새 형상 기록/옛 형상 거절을 확인했다. 실제 재연결 시나리오 전체 검사는 아니다. 일반4인 접촉 경로를 바꾼 것은 아니다.

Relay4대·저사양·사람의 빠른 경계 회피·최종 플레이 경험은 미검증이다. 이 한계를 자동/로컬 LAN 통과로 대체하지 않는다.
