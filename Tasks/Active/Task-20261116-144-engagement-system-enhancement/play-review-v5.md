# v5 검토 — 낮은 톤·개별 음량·한 구역 관객

## 적용
- 환호/야유: 같은 사람 원음 4종씩, 원음 대비 -3/-4반음으로 오프라인 편집. 재생 속도 변경에 의한 음색 조정이며 새 사람 녹음이나 AI 목소리를 생성한 것은 아니다. 게임에서는 pitch=1, 짧은 잔향·객석 방향감 유지.
- 설정 → 사운드: 관객 환호 / 관객 야유 / 관객 웅성거림 음량 0–100%. 기존 전체·효과음 음량을 함께 따른다. 적용 시 이 PC에 저장하며, 취소와 탭 기본값 복구는 기존 편집 방식과 같다.
- 현재 청취 예시: private `AudienceReactionsTask144/audition-heavy-reactions-v5.wav`. 14초, 웅성거림 → 환호 → 야유. 실제 게임의 거리·방향 처리를 포함하지 않는다.

## 1단계: 한 구역 동작
- 72명, Renderer/Material/Mesh 각 1개, 864삼각형. 개별 사람 GameObject/Animator/Collider/NetworkObject 없음.
- 환호: 팔을 들고 한 번 파동. 야유: 앞으로 숙였다가 복귀. 야유에 환호 같은 잔떨림을 넣지 않는다.
- 120ms 동안 여러 사람의 사건을 모으고, 한 동작을 마치는 1.9초 간격을 둔다. 가장 큰 실제 증감량 우선, 동률은 야유. 공유 객석의 시험 우선순위이며 점수 규칙은 변경하지 않는다.
- 개인 소리·팝업은 본인/현재 관전 대상만 유지한다. 다른 사람의 반대 반응이 섞이지 않는다.

## 2단계: 일반 카메라 확인
- 외줄/대포 각각 실제 공연에서 정지·환호·야유를 캡처했다. 검사 동안 같은 구도를 비교하려고 플레이어 이동을 멈췄으며 별도의 근접/확대 카메라를 쓰지 않았다.
- 구역은 1920×1080 화면의 상단 약 300px 폭/50px 높이 안에 들어온다. 움직임은 보이나, 특히 야유 방향을 공연 중 한눈에 구분하기에는 약하다.
- 따라서 **주 피드백은 원래 팝업+사운드**, 관객은 분위기 보조로 판단한다. AI의 화면 검사 결과이며 사람의 블라인드 플레이 판독 시험을 통과했다고 주장하지 않는다.
- [외줄 환호](Previews/Runtime/tightrope-crowd-cheer-v5.png), [외줄 야유](Previews/Runtime/tightrope-crowd-boo-v5.png), [대포 환호](Previews/Runtime/cannon-crowd-cheer-v5.png), [대포 야유](Previews/Runtime/cannon-crowd-boo-v5.png).

## 3단계: 측정 방법
- 전용 Development Windows 빌드. `CURTAINCALL_AUDIENCE_BENCHMARK` 정의와 `-audience-benchmark` 실행 인자를 모두 사용한 경우에만 자동 측정한다. 일반 플레이 빌드에는 측정 클래스가 포함되지 않는다.
- 1280×720, 같은 외줄 카메라, VSync off/프레임 제한 없음. 8초 예열 후 관객 off/on/off/on 네 번, 구간당 4초 중 첫 0.5초 제외. 1인부터 시작한 뒤 같은 PC에서 호스트+클라이언트 3개를 실행한다. 짧은 구간의 탐색 측정이므로 정밀 비용 상한 검증과 구분한다.
- 앞선 긴 실행은 정지한 참가자가 공연 도중 죽고 다음 공연으로 전환되어 조건이 깨졌다. 해당 실행의 전체 프레임 수치는 채택하지 않는다. 최종 진단은 사망/공연 종료가 섞인 구간을 invalid로 기록하고 예외 발생 시 오류 파일을 남기며 종료한다.
- 4인 동시 실행은 같은 CPU/GPU를 공유하는 로컬 연결 검사다. 서로 다른 PC·인터넷 지연 환경의 성능을 대신하지 않는다.
- 기록: 프레임/CPU/GPU p95, draw call, 전체 프레임 GC, 관객 Observe만의 할당, 구역 최초 생성 시간, 전체 공연 진입 시간, 기존 transport 수신량. 전체 진입 시간이나 전체 통신량을 관객 추가 비용으로 단정하지 않는다.
- 최종 기준 빌드: dev `e7564308`, Windows Development, 오류 0/경고 32, 증분 100.216초. 빌드 시간은 게임 로딩 시간이 아니다.

### 1인 탐색 측정
- Ryzen 7 9700X / RTX 5070 Ti / RAM 31GB, 1280×720. 네 구간 모두 사망·공연 전환 없이 유효, 구간당 854–886프레임.
- 메인 스레드 p95: off **5.43 / 5.68ms**, on **5.39 / 5.40ms**. GPU p95: off **1.37 / 1.41ms**, on **1.39 / 1.38ms**. 이 짧은 실행에서는 뚜렷한 악화가 없었지만, 음수 차이를 최적화 효과로 해석하거나 0.3ms 상한 통과로 단정하지 않는다. Render Thread 카운터는 미지원(null).
- 구역 생성 **0.0487ms**, 메시 **163,520B(약160KiB)**, 렌더러 1개/864삼각형/NetworkObject 0개. 이는 준비된 프리팹 인스턴스 생성 비용이며 디스크 첫 로드 지연을 검증한 값은 아니다. 공연 진입은 2.51초이나 관객 추가 로딩 비용으로 해석하지 않는다.
- 마지막 반응 지연 약 **121ms**(의도한 120ms 사건 묶음 포함). 4인 스냅샷을 미리 만든 뒤 `Observe` 130회는 **0B / 총0.2003ms**. 이 함수 이외의 게임 전체 프레임에는 할당이 있으므로 게임 전체 GC=0이라는 의미가 아니다.
- 추가 관객 RPC/NetworkObject는 구현상 없고 기존 호응 상태를 사용한다. 1인 수신 0은 4인 통신 비용 검증이 아니다.
- 원본 수치: [benchmark-single-v5.json](Previews/Runtime/benchmark-single-v5.json).

### 4인 확인과 채택 판단
- 같은 PC 호스트+클라이언트 3개를 두 번 실행했다. 두 번째는 네 명의 로컬 캐릭터 생성/슬롯 할당 완료까지 기다린 뒤 공연을 시작했다. 그래도 클라이언트 3개가 공연 UI/보상/코스 준비에서 90초 초과로 종료했다. 초기 준비 대기만으로 해결되지 않았고 정확한 진입 실패 원인은 미확정이다.
- **4인 프레임·통신·로딩 검증 미완료.** 실패 실행은 성능 표본에 넣지 않았다. [실패 기록](Previews/Runtime/benchmark-four-v5-failure.txt). 호스트와 클라이언트 테스트 프로세스는 모두 종료했다.
- 초기 동기화 보완 빌드도 오류0/경고32, 94.750초 성공. 측정용 정의/Frame Timing 설정은 원복했으며 일반 빌드에서는 자동 실행되지 않는다.
- **확대 보류, CrowdTrial 기본 false 유지.** 한 구역은 가볍게 구성됐지만 야유 판독이 약하고 4인 검증이 끝나지 않았다. 현재 적용한 기존 팝업+개별 소리를 핵심 피드백으로 사용한다.
- 후속은 ① 4인 공연 진입 원인 분리/수정 후 재측정 ② 같은 한 구역의 동작 실루엣·대비만 A/B ③ 사람이 조작 중 반응을 알아보는지 확인 후 채택 여부 결정. 인원/구역 확장은 그 이후다.
