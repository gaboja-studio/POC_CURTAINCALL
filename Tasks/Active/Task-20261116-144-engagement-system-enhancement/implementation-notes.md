# 호응도 피드백 구현 검토안

2026-11-16 사용자 피드백 반영. 아래 수치와 구조는 제안이며, 게임 적용/성능 측정 결과가 아니다. 우선순위는 **작은 점수 팝업 → 자연스러운 소리 → 효과가 확인되는 군중 연출**이다.

## 현재 근거와 판단
- 기존 `PerformanceFeedback.Observe`는 로컬 플레이어의 `ReactionSequence`·`ReactionDelta`·`ReactionAmount`를 소비한다. 초기/재동기화·사망·이탈·메뉴/관전 필터가 있다. 현재 큐는 최대 4개, 만료 3초다.
- `PerformanceRewards.Publish/SendState`와 `RewardMessages.cs`는 이미 해당 값을 신뢰성/순서 보장 상태 메시지로 전송한다. `AudienceReacted`는 호스트 변경 경로의 이벤트여서 그것만 구독하면 참가자 표시가 빠질 수 있다.
- 실제 저장 화면에서 관객석은 높고 멀다. 확대도에서 보이는 자세 차이를 공연 중 인지할 것이라고 가정하지 않는다. 군중은 분위기 보조이며 점수의 유일한 피드백으로 쓰지 않는다.
- 앞선 도장/공연표 안과 금속성·모음 합성 음향은 기각된 시안이다. 코드 합성 소리를 실제 사람 군중 소리의 대체재로 재사용하지 않는다.

## 1. 숫자 팝업 — 먼저 구현할 핵심
- 내용은 실제 증감 `+12`/`−5`만. 공연표·도장·카피·별·토마토·박수 그림·배경 박스 없음. 상아색 증가/탁한 붉은 감소와 명시적 부호, 얇은 어두운 외곽선으로 구분한다.
- A안은 기존 균형 게이지의 바깥 위/옆, B안은 좌상단 호응 게이지 옆. 먼저 A안으로 조작 중 인지를 비교한다. 캐릭터·앞쪽 외줄·균형 판독·조작 가이드와 겹치면 안전 영역으로 이동한다. 대포는 균형 게이지가 없어도 동일한 HUD 주변 안전 영역을 쓴다.
- 1920×1080 기준 약 24~28px 글자, 한 줄 최대 약 100×32px를 시작값으로 잡는다. 0.08초 등장 + 0.55초 유지 + 0.22초 사라짐, 이동은 최대 6px. 통상 1줄, 반대 부호가 겹칠 때만 최대 2줄. 해상도/화면비/글자 크기에 맞춰 조정한다.
- 첫 사건은 다음 UI 갱신에 즉시 표시한다. 이후 0.2초 안의 같은 부호 사건은 **실제로 수신한 변화량만** 합친다. +10과 −5를 +5로 상쇄하지 않는다. 매 이벤트 Instantiate/Destroy·TMP 재질 생성·Canvas 전체 재구성을 피하고 미리 만든 두 슬롯을 재사용한다.
- 총 호응 게이지는 기존 점수를 계속 표시한다. 개인 팝업은 본인 사건만 표시한다. 상한의 실제 증가량 0은 거짓 +1을 만들지 않고 게이지의 짧은 반응만 허용한다. 0점 야유 금지·자연 감소/재동기화 제외·메뉴/관전 중 숨김을 보존한다.
- 사건 번호가 건너뛰면 누락량을 점수 차이로 추정하지 않는다(자연 감소가 섞일 수 있음). 최신 검증된 사건만 표시하고 합계는 최신 상태를 따른다. 이 경우가 정상 통신에서도 발생하면 표시 이벤트 보존 경로를 별도로 보완한다. 손잡기 정보 알림은 점수 팝업과 분리한다.

## 2. 소리 — 사람의 반응으로 다시 시작
- 실제 녹음 또는 사용 권리가 확인된 군중 소스를 우선한다. 합성 파형·금속성 두 음·팡파르·과도한 피치 변조는 빼고, 환호는 사람의 짧은 함성과 불규칙한 손뼉, 야유는 사람의 낮은 우우 소리와 드문 발 구름으로 구분한다.
- 각 2~3개 변형, 본체 약 1~1.8초와 짧은 잔향을 출발점으로 한다. 원음을 먼저 블라인드 청취해 자연스러움/방향을 통과한 뒤 공간 잔향을 붙인다. 길고 어두운 잔향으로 어색한 원음을 숨기지 않는다.
- 큰 군중 파일을 무조건 레이어링하지 않는다. 이미 섞인 한 클립 + 선택적 짧은 원음 정도로 제한한다. 사용자는 동의하지 않은 플러그인을 설치하지 않으며, 현재 가능한 녹음/보유 소스 기반 제작을 우선한다. 생성 프롬프트는 `Previews/sound-prompts-v2.md`에 보관한다.
- 본인 점수 음향을 우선한다. 팀원의 반대 반응이 동시에 나면 공유 객석 음향을 낮추거나 생략해 내 증감의 의미를 흐리지 않는다. 개인 음향과 환경 음향이 같은 클립을 중복 재생하지 않게 한 조정기가 관리한다. 친구 음성/위험 소리에는 덕킹을 걸지 않는다.
- 고정 AudioSource 풀 3개 이내, 로컬 사건 우선, 같은 방향의 밀집 사건은 병합하고 긴 연출은 약 1.5~2초 최소 간격을 시험한다. 재생 도중 큰 피치 변경은 하지 않는다. 메뉴/씬 종료에서 잔여 큐를 비운다.
- 짧은 클립은 사전 로드/디코드하고 메모리를 측정한다. 배경 로드만 켜면 첫 Play가 지연될 수 있으므로 `loadState`를 확인한다. 아직 준비되지 않은 선택 연출은 생략하며 오래된 소리를 로딩 완료 뒤 늦게 재생하지 않는다. [Unity 음향 로딩 문서](https://docs.unity.com/en-us/engine/6000.3/manual/audio/reference/class-audio-clip)

## 3. 군중 — 한 구역 시험 뒤 채택
- 첫 시험은 화면에 보이는 객석 한 구역뿐이다. 저해상도 불투명 인간 실루엣, 중립/환호/야유 세 자세를 준비한다. 사람별 GameObject·Animator·SkinnedMeshRenderer·Collider·NetworkObject를 만들지 않는다.
- 채택 시 객석을 약 8~12개 공간 구역으로 나누고 각 구역을 미리 합친 MeshRenderer로 저장한다. 같은 위상의 세 자세 좌표를 가진 간단한 셰이더로 중립→일어남/팔 들기 또는 난간 쪽 기울임을 보간한다. 개별 머리·손 추적이나 군중 AI는 없다. 과도하게 허리를 숙여 인사처럼 보이지 않는지도 확인한다.
- 구역/개체 변형 시점은 미리 저장한 seed와 위상으로 분산한다. CPU는 활성 구역의 사건 종류/시작 시간만 갱신하고 개별 사람을 매 프레임 순회하지 않는다. 셰이더 변형 범위를 포함한 bounds를 설정하고 카메라에서 안 보이는 구역은 그리지 않는다. 먼 구역은 정지 자세로 유지한다.
- 공용 재질 1개와 작은 공용 텍스처를 시작점으로 한다. 구역 ID를 정점에 저장하고 작은 상태 배열을 사용해 매 객체의 MaterialPropertyBlock을 남발하지 않는다. SRP Batcher/URP 호환을 확인하며 프로젝트 전체 렌더 옵션을 이 작업 때문에 바꾸지 않는다. [Unity 최적화 선택](https://docs.unity.com/en-us/engine/6000.3/manual/analysis/graphics-performance-profiling/reduce-draw-calls/optimizing-draw-calls-choose-method)
- 그림자·물리·추가 실시간 광원은 끈다. 어깨/난간의 밝기 변화는 재질 표현으로 작게 준다. 넓은 반투명 판과 겹치는 파티클은 피한다. 한 덩어리로 돔 전체를 합치면 안 보이는 부분까지 그려질 수 있어 공간 구역을 유지한다. [메시 결합과 컬링 제약](https://docs.unity.com/en-us/engine/6000.3/manual/analysis/graphics-performance-profiling/reduce-draw-calls/draw-call-batching/draw-call-batching)
- 실제 조작 중 시야 밖에 있거나 대부분 못 느끼면 군중 애니메이션을 중단하고 정적인 관객과 소리만 남긴다. 조명 확대·카메라 이동·거대한 군중으로 억지로 눈에 띄게 만들지 않는다.

## 4. 네트워크·로드 경로
- 1차안은 기존 호응 스냅샷을 읽어 각 PC에서 연출만 수행한다. 관객용 추가 메시지/매 프레임 위치 전송은 0개를 목표로 한다. 점수 판정은 그대로 호스트 권한이다. 가벼운 연출을 위해 기존 전체 보상 상태를 추가 Publish하지 않는다.
- 공연 ID+참가자 ID+반응 번호로 중복을 제거하고 고정 해시로 구역/변형을 고른다. 첫 수신·재동기화는 기준점만 잡고 이전 반응을 재생하지 않는다. 연출 미준비/비활성 중에도 최신 번호는 소비한다. 큐 폭주 시 오래된 공간 연출을 생략하며 판정/현재 점수에는 영향을 주지 않는다.
- 이 방식은 동일 사건/의미를 공유하지만 시작 프레임까지 같지는 않다. 전송 지연만큼 차이가 생기며 구역 병합도 수신 시점에 따라 달라질 수 있다. 시각 장식에는 허용하고, 일치 자체가 필요한 것으로 실측될 때만 기존 메시지에 호스트 시각/연출 ID를 넣는 별도 변경을 검토한다.
- 재접속/새 씬 초기화 후 과거 상태를 재연하지 않는다. 긴 패킷 지연에서 늦은 반응을 충분히 걸러내지 못하면, 타임스탬프 없는 현재 상태의 한계를 기록하고 공유 군중 효과를 비활성화하는 쪽을 우선한다. 감점/보상 메시지를 비신뢰성으로 바꾸지 않는다.
- 배치 메시·자세·좌석 seed는 에디터에서 굽는다. 플레이 중 군중 생성/메시 결합/외부 다운로드 없음. 선택 군중 리소스는 기존 준비 구간에서 비동기 준비하며, 초기/후속 로드 시간을 각각 측정한다. 준비가 늦으면 군중을 생략하고 공연 시작을 기다리게 하지 않는다.
- GPU 최초 업로드/셰이더 사용과 음원 최초 디코드도 첫 반응 테스트에 포함한다. 비동기라는 이름만으로 끊김이 없다고 판단하지 않는다. 반응 중 준비 자원을 생성·해제하지 않고 공간 체류 동안 재사용한다.

## 5. 채택 조건과 순서
1. **기준 측정:** 사용할 테스트 PC/해상도/그래픽 설정을 기록하고 동일 외줄·대포 구간의 기존 프레임/로드/메모리/통신량을 저장한다. 최소 사양은 아직 확정 근거가 없으므로 아래를 보장값으로 쓰지 않는다.
2. **팝업·음향:** 개인 사건으로 연결해 A/B 위치와 원음 2~3종을 비교한다. 통상 시야에서 방향 확인 약 0.5초 이내·무작위 20건 중 18건 이상 구분을 임시 목표로 한다. 소리만 듣는 시험과 실제 대화하며 조작하는 시험을 분리한다.
3. **한 구역 비교:** 같은 소리/팝업 조건에서 정적 군중과 움직이는 군중을 비교한다. 보라고 알려주지 않은 실제 플레이에서 존재감·압박감이 달라지는지 확인한다. 차이가 불분명하면 이 단계에서 중단한다.
4. **성능/통신:** 4인 동시 반응·최대 시야·카메라 회전·첫 반응·씬 재진입을 시험한다. 호스트/참가자 각각 기록하고 지연/손실 환경에서도 점수·중복·과거 재생을 확인한다.
5. **임시 비용 상한:** 군중 추가 Main Thread p95 ≤0.3ms, GPU p95 ≤0.5ms, 첫 반응 프레임의 추가 시간 ≤2ms, 반복 처리 managed GC 0B/frame 목표. 색상 패스 약 12 draw calls 이내(추가 패스는 별도 계수), 추가 메모리 16MB 이내(군중+짧은 오디오, 측정 포함), 동일 조건 로드 p95 증가 ≤0.2초. FPS 평균만으로 통과 처리하지 않는다. 기준 초과 시 밀도/구역/자세를 줄이거나 효과를 제거한다.
6. **최종 판단:** 눈에 잘 안 띄거나 체감 개선이 작으면 군중은 정적으로 유지한다. 핵심 피드백은 작은 숫자 팝업과 사람 소리만으로 완결돼야 한다. 재미·억압감은 사람 검토, 성능은 실행 빌드 측정으로 각각 확인한다.

## 후속 구현 지점
`PerformanceFeedback`의 표시 큐와 `HudUIManager.ShowScoreFeedback`, 실제 `Feedback` 프리팹을 수정 후보로 한다. `C1CheerGaugeView`는 점수 표시 계약을 유지한다. 음향 조정기와 선택적 구역 렌더러를 분리하고 공통 조정값은 `GameSettings.Base` 경로로 제공한다. private 키트 원본은 덮어쓰지 않는다. 실제 수정 전 code-folders/asset-ownership과 사용자 변경을 확인한다.
